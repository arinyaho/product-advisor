# Company context service

TL;DR: Run company source storage and LightRAG inside the company environment. A single-reader pipeline excludes Slack DMs and automatically publishes completed Notion/Drive captures through validated, budgeted batches. The public book MCP stays separate. Configure the reader, collection start, model budget and private file paths before enabling the hourly units. This is not a multi-user authorization system.

## Data boundary

- Source records, embeddings, graphs, extraction caches and receipts stay on the company host. Never deploy this directory's runtime data to the public book server.
- Internal OpenAI-compatible models are supported. External model processing is disabled unless `external_provider` explicitly equals `openrouter`; only `https://openrouter.ai/api/v1` is then permitted as an external endpoint. OpenRouter receives source text during extraction/embedding and queries during retrieval. This is not fully on-premises inference.
- Model credentials and the MCP bearer token are read from files, never command arguments. The MCP token file must have mode `600`.
- The server binds to loopback. Reach it through an authenticated company tunnel or an internal TLS proxy. Do not expose it publicly.
- DNS checks reject public model destinations by default. Network egress controls must enforce the same policy; application DNS checks alone cannot prevent DNS rebinding.
- A token grants access to the snapshot for its named reader. Do not share it or aggregate different readers' material. With `--access-state`, every evidence read checks the latest channel inventory; revoked access or an inventory older than two hours blocks retrieval. This is hourly ACL polling, not a source-provider check on each query. With `--sync-state`, a known source revision/removal blocks the old snapshot until its replacement is validated. Historical private artifacts remain on disk until an operator applies the company's retention policy; exclusion from retrieval is not erasure from backups or an external model provider.

## Initial Notion capture

- `python -m company_context.collect_notion --token-file <private-file> --database <private-sqlite> --workspace-id <authorized-workspace>` captures pages accessible to the configured integration, without a date cutoff. Integration access is not proof of a human reader's Notion ACL. The operator must explicitly authorize that integration's shared pages for the single MCP reader before configuring automatic publication.
- The pinned API version is `2025-09-03`. The collector searches accessible pages/data sources, queries database rows, recursively reads blocks and synced blocks, and paginates supported page properties. Objects retain their source IDs, content hashes and capture times; parent task membership preserves traversal order.
- API pagination and consumed item positions, including omitted items, are checkpointed together in SQLite. Re-running the command resumes pending tasks, without replaying completed tasks. List response metadata retains rollup aggregates and unsupported calculation reasons. Formula properties use their dedicated endpoint. An API-reported incomplete data source query remains a failed task instead of claiming full coverage; narrower query partitioning requires operator follow-up.
- Capture schema 2 refuses to resume older archives, whose property positions and traversal coverage cannot be reconstructed reliably. Retain the old database and start a separate schema-2 capture. Failed tasks remain visible and require operator inspection; this is an initial capture, not periodic synchronization or deletion propagation.
- After backing up the archive and stopping its collector, use `--retry-validation-errors` once to audit and requeue existing HTTP400 reads at their saved cursors. Unknown validation errors remain failed; other failures are not retried. SQLite WAL mode allows the publisher's consistent read transaction while the collector commits new objects.
- Comments denied by the API, unsupported blocks and credential-pattern omissions are explicitly recorded. The exact API validation errors for unsupported external page bodies and invalid rollup relations become endpoint-specific omissions; other HTTP 400 responses remain failed tasks. Exported text marks these unavailable fields instead of inventing an empty value. An omitted parent payload does not suppress traversal of its structural child IDs. Temporary hosted file URLs are removed using expiry metadata and recognized signing parameters. File attachments are not downloaded. Credential-pattern matching is a heuristic, not a guarantee that arbitrary secret formats are absent.
- API search is not an atomic or guaranteed exhaustive workspace export. Page metadata counts do not mean page bodies are complete. `finished_at` means the task queue was attempted; check failed tasks and omissions before accepting coverage.
- The raw collector makes no model calls. Bounded retries cover HTTP 429 and transient 5xx reads; final failed tasks still require operator inspection. Completed captures retain their original completion timestamp across restarts. Adapt `systemd/company-notion-capture.service` with the authorized workspace ID; its completion hook requests the separate validated publisher described below.

## Drive capture and automatic document publication

- `collect_drive` verifies the Google account and stable permission ID through Drive `about`, then enumerates the user's corpus and accessible shared drives separately. A failed/incomplete listing cannot become a complete capture. File IDs deduplicate shared entries; shortcuts queue their targets, whose access is checked independently.
- Native Docs use text runs across tabs; native Slides include slide/table/notes text; native Sheets export all worksheets. PDF text layers, DOCX body paragraphs/tables, XLSX values/formula expressions, PPTX text/tables/notes and UTF-8 text are supported. Images/OCR, HWP, unsupported MIME types, oversized/empty files and parser failures are explicit omissions. No source files or sharing settings are modified.
- Downloads are bounded to 50 MB. Document extraction runs in a subprocess with a 70-second wall limit, 60-second CPU limit and 2 GB address-space limit. Office expansion is bounded to 200 MB and extracted text to two million characters. File version and modification time are checked before and after reading. Revision races/API failures remain failed tasks, not accepted partial sources.
- By default the document publisher refuses captures with pending or failed tasks. With Notion `allow_partial: true`, each exported page requires its page read, every scheduled property read, and recursively rendered child/synced-block reads to be complete. Unfinished pages are deferred; comments remain raw-only and do not block page export. A stable capture ID prevents a different unfinished capture from replacing already published managed sources. Per-source capture timestamps remain stable as unrelated pages finish. Coverage distinguishes pending pages/tasks, API omissions, and capture completeness. Notion exports paginated property values and ordered block text; oversized or credential-pattern pages are explicit export omissions. Drive still requires a completed capture and exports only successfully captured text; native spreadsheet export-size limits are explicit omissions. Provider identities are pinned in each record. Static aliases are replaced only for the same resource; unrelated sources survive.
- Completed providers begin indexing independently. Defaults allow 500 new sources and two million new characters per batch, newest edits first. Providers alternate when both have pending sources. MCP coverage distinguishes available sources, indexed sources and `index_complete`; metadata discovery and raw capture are not index completion.
- Publishers serialize through `sync.lock`, share `sync-model-receipts.jsonl`, and call the same native validation and authenticated MCP acceptance path. Slack refreshes preserve published document records. Completion hooks request publication; a 15-minute timer catches a busy publisher or continues the next batch. It does not replay failed paid builds. A long active Slack sync can delay the next document batch.
- Private `document-sources.json` becomes the common ingestion budget authority once configured. Both publishers read its `budget_usd`. A budget/provider/build failure leaves the last validated release in place unless known withdrawals require blocking it. The budget does not guarantee that every captured source will fit.
- `company-document-access.timer` refreshes provider permissions hourly, including building candidates. It checks Notion pages/original synced blocks and Drive identity, file visibility and download capability. Missing, mismatched or older-than-two-hour inventories block model dispatch and evidence reads. Confirmed revocations persist even if a later provider refresh fails. This is bounded-staleness polling, not a provider call on each query. Revocation/source changes can require operator repair or a new capture; document content synchronization is outside this initial-capture pipeline.
- Notion batches with at most 100 required page/block identities use direct access checks; larger sets retain paginated search followed by direct reads for missing identities. Withheld page metadata without retained body text is excluded rather than indexed under a generated title; only the omission count is exposed.
- Releases, archives, credentials, receipts and logs stay on the company host. Release retention remains an operator responsibility; batched immutable releases consume additional disk space.

Live access checks exclude archived or unreadable pages and unavailable synced-block dependencies before model dispatch. Denied records remain pending and are retried after untried records, oldest access check first; a denied-only batch still yields to the next document provider. Revoked published records are withdrawn even when their capture has not changed. Use the company host and its authorized Mien profile to capture one explicit Jira Cloud project and update date. The date starts at midnight in the reader's configured Jira timezone. The collector uses read-only Jira API requests and writes a new capture in a private directory. An incomplete result, out-of-scope update, repeated issue, or exceeded issue or page limit leaves no output file.

To opt in to publication, add the `jira` provider to the existing private `document-sources.json`. ## Source snapshot

The input is JSON with `principal` and `records`. Every record has `source_id`, `source_type` (`slack`, `docs`, `jira`, `notion`, `user_update`), `url`, `title`, `author`, `occurred_at`, `updated_at`, `collected_at`, `record_kind`, and `text`.

- `source_id` is the source system's stable identity, namespaced by system/workspace. Duplicate identities within a snapshot are rejected.
- Slack records require API-derived `slack_conversation` metadata with the matching `id`, boolean `is_im`, `is_mpim`, and `is_private` fields, and `is_member=true` for private channels. One-to-one and group DMs, direct-DM source links in attributed summaries, and unknown conversation types are rejected before snapshot creation or model calls. Legacy snapshots without conversation classification must be re-collected and rebuilt. Public channels need not be joined; private channels must be accessible to the named reader. Collection must request only `public_channel,private_channel` and recheck these flags before reading message bodies.
- `text` preserves the connector's fetched text representation. Chunk offsets address this captured representation, not original provider byte offsets.
- Unknown author, event time and edit time are explicit `null`. Collection time is required. Known times include timezone information; an edit timestamp is not an event timestamp.
- `record_kind` is `source` or `summary`. Summaries also require `derived_from`, containing source URLs. Neither kind establishes that every assertion is true.
- Optional `coverage` describes omitted comments, child pages, attachments or other uncollected material. Do not represent a selected excerpt as the entire source.
- Credentials must be excluded before collection. Customer records, registrations, private evaluation questions and runtime files must not enter Git.
- The memory bounds are 0–100,000 records, two million characters per source and 100 million characters per snapshot. Exceeding a bound fails the entire build rather than truncating coverage. New snapshot directories are required for changes; an existing directory is never overwritten. An empty capture is valid and retires the last source without model calls; document publication inherits that verified coverage. Failed builds retain their evidence and do not acquire a `ready.json` marker.

## Extraction and retrieval

- LightRAG 1.5.7 uses its default extraction prompt, entity types and extraction limits. No reviewed ontology, customer schema or manual graph is injected.
- Imported legacy sources retain their 1,600-character chunks. New Slack captures group each thread separately; unthreaded channel messages form bounded timeline windows: at most 30 minutes from the first message, 100 messages, or 32,000 rendered characters, also split at UTC date boundaries. One long message remains intact as a source and is split by the existing chunker. Timeline proximity is not a claim of a common subject. Threads and timelines never mix, nor do different channels. Explicit bot/system-only groups stay in the raw archive but are excluded from the graph. A thread with human participation retains every captured reply, including bot replies. Unknown authors are retained. Collection coverage reports eligible/excluded messages and the versioned policy. An unchanged-record capture updates a snapshot-bound coverage receipt so MCP status reports current capture-through and omission counts without model calls.
- Slack chunks target 3,200 characters and end at message boundaries. A single oversized message is split at a paragraph/sentence boundary when one is available, otherwise at the hard character bound. Captured text and offsets reconstruct exactly; no LLM summary replaces the originals. Each included message retains its author ID, event/edit times and permalink. Later chunks include up to 1,600 characters of the original opening message as explicitly bounded context, plus `root_chunk_id` and previous/next handles. An opening message outside the capture interval is marked missing, never invented. These are character bounds, not claimed token counts or a measured retrieval optimum.
- Native custom-chunk insertion preserves document-scoped source identities. Build completion and serving startup validate exact chunk identities/content, processed document status, and every graph reference against the authorized snapshot. Each release has a separate LightRAG workspace so in-process storage caches cannot cross releases. The immutable snapshot retains original whitespace and HTML entities for exact source reads.
- `search_company_context(query, mode="mix", k=5)` accepts natural-language questions. `mix` and `naive` use the same source snapshot. Retrieval does not silently fall back and does not generate an answer.
- Context version 3 adds `graph` descriptions to `mix` responses without reducing the original `results`. Entity and relationship descriptions alternate in native rank order within a separate 6,000-token budget. `graph_coverage` reports omitted and untraceable records; it is not completeness of the company corpus. Oversized descriptions are omitted intact, not cut into partial assertions. `naive` returns an empty graph.
- Every graph record is marked model-derived. Its `sources[].read_source` arguments lead to exact originals through `get_company_source`, including passages outside the first `k` chunks. Source metadata retains actor, event/edit/collection times, summary attribution and coverage. Unresolved references are counted; records with no traceable original are excluded. Graph extraction timestamps are not substituted for source event times.
- `get_company_source(chunk_id)` returns the captured passage, metadata and previous/next chunk handles for reading the surrounding source or a full thread. Handles never cross source identities. `company_index_status()` reports the snapshot identity, reader and collection coverage.
- Returned passages are candidates requiring source review. A match is not proof of purchase intent, a graph edge is not an established fact, and no matches do not prove the company has no evidence.

## Configuration and execution

Create a private JSON configuration on the company host. Set `chat_url`, `embedding_url`, `chat_model`, `embedding_model` and `dimensions` explicitly. Optional `chat_key_file` and `embedding_key_file` point to credential files. For authorized OpenRouter use, add `"external_provider": "openrouter"` and use its exact API base URL for both endpoints. There are no default public model endpoints.

From the code root:

```sh
uv venv .venv
uv pip install --python .venv/bin/python -r company_context/requirements.txt
.venv/bin/python -m company_context.server build --config /private/models.json --input /private/snapshot.json --directory /private/releases/pilot-1 --max-model-calls 200 --budget-usd 5
.venv/bin/python -m company_context.server serve --config /private/models.json --directory /private/releases/pilot-1 --token-file /private/mcp-token --port 8766 --max-model-calls 1000 --budget-usd 5
```

Automatic ingestion requires `cost_ceiling` for both configured models. Each entry pins `model`, `context_tokens`, `max_price` (`prompt`/`completion` per million tokens and `request` per request), and a `cache_multiplier` covering the highest cache-write price. Reserve the full context at these maximum rates plus capped output before dispatch, apply OpenRouter `provider.max_price` to every eligible provider, then replace the reservation with reported usage cost. Validate these limits against the actual model catalog before deployment; model changes require updated ceilings. A provider charge above the reservation is retained and stops further calls. Legacy standalone evaluations without ceilings retain fixed $0.10/$0.02 estimates; they are not hard billing caps. The append-only receipt ledger flushes a pending reservation to disk before dispatch and a final event afterward; restart restores the latest event per call, including legacy single-event receipts. Reservations reread the ledger under an exclusive file lock so another service process cannot reuse a call ID or dispatch over an unfinished reservation. This service requires a Unix host and a local filesystem supporting `flock`. Failed, cancelled, or unfinished requests stop further model calls until operator review. Receipts contain model, status and usage; no request bodies or credentials. Inspect failed receipts before explicitly starting a new attempt; restarting does not reset the budget. Production usage limits require operator configuration after pilot acceptance.

Chat requests allow OpenRouter to fall back to another provider of the same configured model within the unchanged price cap, required parameters and account restrictions. Embedding provider fallbacks remain disabled. There is no local retry. OpenRouter documents that failed model attempts are not charged under [Zero Completion Insurance](https://openrouter.ai/docs/guides/features/zero-completion-insurance); the ledger still records reported usage, retains full reservations for unresolved failures, and stops on an above-reservation charge. Provider billing errors cannot be excluded by this client.

Receipts retain the HTTP status and exception type without provider response bodies. HTTP errors additionally retain bounded integer Retry-After/X-RateLimit headers and fixed known error-type, limit-source and reason values. A provider-code presence flag records only that the field exists, not its value or the cause of the failure. Arbitrary messages, metadata, provider codes, malformed values and noninteger headers are omitted. After investigating a failure, an operator can append a receipt for the same call with `status=reviewed_failure_cost_reserved` and a nonempty `operator_review`, retaining its full conservative cost. Restoration uses the maximum reserved cost from the original failure history for a reviewed failure, even if the appended review incorrectly supplies a smaller amount. The original failure remains in the ledger. This is never automatic; restarting after that explicit review permits new calls within the remaining cumulative budget. A failed sync candidate still requires separate operator review and a new attempt identity.

HTTPX model requests use a 180-second inactivity timeout, not a total request deadline. LightRAG 1.5.7 receives the same embedding timeout setting, producing a 360-second worker deadline instead of its default 60 seconds. A request that continues transferring data can still exceed the worker deadline; cancellation retains its full reservation and stops subsequent model calls without automatic replay.

For Codex access, run `company_context.proxy` over authenticated SSH to the company host with `--token-file /private/mcp-token`. If the service uses a different port, pass the same `--port` to the proxy; both default to `8766`. The proxy reads the token on that host and connects to the loopback HTTP service. No token or company corpus is copied into the client configuration.

## Advisor integration and acceptance

1. Read company evidence through the internal MCP, including dates, authors, coverage and conflicting records.
2. Keep confirmed observations, hypotheses and missing information separate. Source summaries do not automatically become customer statements.
3. Ask the public book MCP generic conceptual questions, excluding customer names, internal facts, quotations, prices and identifiers. Read returned book passages before citing them.
4. Combine both evidence sets in the authorized user's session. Name the next action, the person/role to ask, the question, and the answer that would change the decision. Preserve unknown buying authority and rejection reasons.
5. Record only user-confirmed actions/outcomes when explicitly authorized; do not index an advisor's suggestion as an accomplished action.

Before a material decision, the advisor reads relevant graph-linked originals and classifies their applicability as `same_scope_replacement`, `different_scope`, `coexisting_perspectives`, or `unresolved`. Replacement requires the same subject and decision scope plus evidence that the earlier position changed or was withdrawn. Newer timestamps alone do not establish authority; different stakeholder opinions coexist. Separate budget paragraphs, customers and internal versus customer decisions remain separate. These are caller-reviewed classifications with source citations, not automated server verdicts or a new graph ontology. The installed Product Advisor skill and both MCP transports carry this workflow.

Freeze evaluation queries and expected source identities before indexing or tuning. Include several opportunities, unnamed semantic questions, changed decisions, conflicting perspectives and unsupported claims. Compare `naive` and `mix` against the same expected sources. Evaluation output contains private evidence and is created with owner-only permissions regardless of the shell's umask. Retrieval tests are not an answer-quality verdict: separately review whether the advisor invents causes, conflates a pilot with a purchase, or misses contradictory evidence.

## Channel capture and hourly synchronization

1. `collect_slack` enumerates `public_channel,private_channel`, validates API flags before reading bodies, and pins the authenticated reader/workspace. Public channels need not be joined; private channels require membership. It scans parent history to discover recent replies under older roots, stores only messages inside the frozen interval, paginates threads, and checkpoints SQLite pages and cursors transactionally. Raw storage is private on the company host. Recognizable credential-bearing messages are omitted; the regex is not a guarantee that all sensitive text is detected.
2. Initial collection resumes the same frozen interval. An expired Slack cursor restarts only that channel from its beginning and clears that candidate channel's stale rows. A channel absent from a newly completed access inventory is retired from the pending capture, so remaining authorized channels can finish. Other failed or incomplete channels prevent export. Coverage reports distinguish channels, complete/failed channels, messages and credential omissions. Collection does not call a model or publish a graph. Slack reads are not an atomic point-in-time snapshot: source mutations during pagination are reconciled in subsequent cycles.
3. Subsequent cycles re-read parent history and compare each thread's reply count/latest-reply signature. Unchanged replies can be reused only when the prior cutoff covered the latest reply, and for at most 24 hours, after which they are fully re-read to detect edits that Slack does not expose in a change cursor. Deleted roots/replies disappear from the next complete capture. Revoked channels are separately blocked through the hourly access inventory. New captures do not copy unobserved old rows into the exported snapshot.
4. Changed source content produces a new document identity. Append-only candidates reuse a validated index only when every previous document remains identical and the index configuration matches. Any changed or removed source requires a fresh graph without copying the old extraction cache: native sequential deletion can otherwise send another withdrawn source into a reconstruction request. This costs more than incremental deletion and remains subject to the cumulative budget. Unchanged source collection provenance stays stable. First migration from the legacy pilot also uses a fresh graph. Slack publication retains unchanged sources and adds newest-activity sources in batches (default 100 sources and 500,000 characters, overridable with `slack_batch_sources` and `slack_batch_characters` in private `document-sources.json`; one source may exceed the character target). `collection.slack_indexing` explicitly reports available/indexed source counts and completeness. Later sync ticks reuse the completed frozen capture until its backfill finishes; channel permissions are refreshed each time. The shared access inventory retains observed revocation times even after reauthorization. Revoked channels are excluded for the remainder of that frozen capture; a fresh collection bypasses the old reply cache after an observed revocation before admitting them again. A pending capture with completed checkpoints is also replaced, preserving its original database, if it predates an observed revocation. The capture-start epoch is checked before every model dispatch, publication and served source read, so reauthorization cannot hide a revocation observed after export. The next content collection starts after backfill completion, so the capture-through timestamp remains the freshness boundary during backfill. Failed extraction, budget checks or acceptance leave the candidate unpublished; no automatic paid replay occurs.
5. A completed bootstrap archive stays immutable. A resumable candidate copy revalidates accessible channels and retires revoked channels before its first publication. Slack dependency URLs must use canonical channel archive links; unsupported Slack URL forms fail closed.
6. `sync` validates the candidate through an authenticated in-process MCP transport before switching `current`, then restarts the loopback service and checks the deployed snapshot and an exact source. If deployed acceptance fails, it blocks the candidate and stops the service. Confirmed withdrawals are recorded before candidate validation or model configuration, including empty or invalid replacement attempts. Non-Slack supplements must explicitly name the same authorized reader; their Slack-derived dependencies are checked before model dispatch. The service must use `--directory /private/current --access-state /private/access.json --sync-state /private/sync.json`. A failed restart/acceptance requires operator repair; there is no automatic rollback to withdrawn evidence.
7. The included user-systemd timers trigger hourly. A long-running job is not overlapped; hourly triggering does not promise one-hour end-to-end freshness. The ACL job runs independently, including during collection/indexing. Both callers serialize their inventory scans under one lock and stamp the scan start time. Every build-time model dispatch rechecks current channel access; already dispatched provider requests cannot be recalled. The single append-only `sync-model-receipts.jsonl` spans all sync generations: the configured budget is cumulative, not reset hourly. Review retained failures before authorizing another paid attempt.

## Work-intent experiment

`compare_context.py` compares vector chunks, graph-selected chunks, and graph descriptions with chunks using a frozen private protocol. It copies an existing snapshot, uses the same answer model and book principles for every arm, and enforces the same maximum company-context token budget. Graph descriptions replace part of the chunk budget. Original extraction and the serving service are unchanged.

Run it on the company host with `--experiment`, `--snapshot`, and `--config`. The new experiment directory must contain `protocol.json` and its exact SHA-256 in `protocol.sha256`. Questions, context budgets, arm order, book principles and the review rubric must be frozen before model calls. Company questions, model requests, provider responses and manual reviews belong only in that private directory. Failed runs are retained; retries require a separately identified run. Generation is bounded to 80 model calls and a $3 conservative stopping estimate, including embeddings.

Review context connections, changed decisions and counterevidence, action relevance, and unsupported claims separately. Citation identity does not establish that a claim is supported. The experiment retains graph-to-original-source references for inspection. Its single-pass answers and same-agent manual review do not establish statistical superiority, independent answer quality, or the behavior of a different final answer model. The production whole-query keyword policy is held fixed; this experiment does not evaluate native keyword extraction or agentic follow-up retrieval.
